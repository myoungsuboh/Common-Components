# ADR-2026-08-10-devextreme-fit-width-proportional: 가로 폭 채우기 기본값과 방식

- 기록일: 2026-08-10 10:45
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: 없음
- 관련 plan: 없음

## 맥락 (Context)

"grid 가로 넓이가 꽉 채워지게 해줘" 라는 요구가 들어왔다. 실제로 카드 폭이 1026px 인데 표는 982px 로 남고 오른쪽에 빈 공간이 있었다.

원인은 DevExtreme 내부 동작이다. `grid_core/views/m_grid_view.js` 는 아래 조건에서 그리드 루트에 **인라인 `max-width`(= 컬럼 폭 합계)** 를 박는다.

```js
if (!hasAutoWidth && resultWidths.length) {          // 모든 컬럼에 width 가 있고
  if (totalWidth < contentWidth) {                    // 폭 합계가 컨테이너보다 좁으면
    resultWidths[lastColumnIndex] = "auto";
    if (false === hasWidth && !hasPercentWidth) {
      that._maxWidth = totalWidth + scrollbarWidth + borderWidth;
      $element.css("maxWidth", that._maxWidth)        // <- 표를 컬럼 합계로 고정
    }
  }
}
```

인라인 스타일이라 CSS `width: 100%` 로는 덮을 수 없다(직접 시도해서 확인했다 — `max-width` 가 이긴다). 반대로 조건문이 **`!hasAutoWidth`** 와 **`!hasPercentWidth`** 를 요구하므로, 폭 없는 컬럼을 하나 두거나 폭을 % 로 주면 제한이 걸리지 않는다.

즉 해법이 두 가지 있고, 어느 쪽을 기본으로 삼느냐가 화면 인상을 결정한다.

## 결정 (Decision)

1. **`fitWidth` prop 을 두고 기본값을 `true` 로 한다.** 업무 화면에서 표가 카드 폭을 꽉 채우는 쪽이 자연스럽다.
2. **채우는 방식은 "비율 유지" 를 기본으로 한다.** 지정한 px 폭을 그대로 비율로 환산해(px -> %) 모든 컬럼이 함께 늘어난다.
3. **컬럼에 `fill: true`** 를 주면 그 컬럼만 `width` 를 비워 남는 공간을 전부 흡수한다. 긴 텍스트 컬럼 하나만 늘리고 싶을 때 쓴다.
4. 어느 방식이든 **지정했던 px 를 `minWidth` 로 남긴다.** 좁은 화면에서는 `minWidth` 까지 줄어든 뒤 가로 스크롤이 생긴다.
5. 폭 계산은 **행번호 컬럼까지 포함한 최종 목록**에서 한다. 컬럼 빌더가 아니라 래퍼가 `applyFillColumn()` 을 호출한다.
6. px 가 아닌 폭(`'30%'`, `'auto'`)이 섞여 있으면 **손대지 않는다.** 사용자 의도를 추측하지 않는다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 비율 유지 (px -> %) | 컬럼 간 폭 차이가 그대로 유지되고 어느 한 컬럼도 기형적으로 넓어지지 않는다. 컨테이너 폭을 몰라도 계산된다 | 지정한 px 가 그대로 유지되지는 않는다(비율만 유지) | 채택 (기본) |
| 가장 넓은 컬럼이 여백을 전부 흡수 | 구현이 단순하고 다른 컬럼은 px 그대로 | **실제로 만들어 보니 결과가 나빴다.** 폭이 비슷한 컬럼들(110/110/110/150/120/120)만 있는 화면에서 급여가 150px -> 394px 로 부풀고 밴드 폭도 330px vs 514px 로 어긋났다 | 기각 (기본에서 제외, `fill` 옵션으로 남김) |
| 폭 없는 컬럼들에 여백을 균등 분배 | 시각적으로 균형 | DevExtreme 이 폭 없는 컬럼에 "평균 폭"을 주므로 의도한 폭 차이가 사라진다(사번 110 과 급여 150 이 같아진다) | 기각 |
| CSS 로 `max-width` 를 덮기 | 우리 코드가 짧다 | 인라인 스타일이라 `!important` 가 필요하고, 표 폭과 DevExtreme 이 계산한 컬럼 폭이 어긋나 헤더/셀이 틀어질 위험이 있다 | 기각 |
| 고정 px 컬럼과 % 컬럼을 섞기 | 행번호처럼 늘어나면 안 되는 컬럼을 고정할 수 있다 | % 는 표 폭 기준이라 고정 px 를 뺀 나머지에 대한 비율을 계산해야 하는데, 컬럼 빌더는 컨테이너 폭을 모른다 | 기각 |
| 기본값을 `false` 로 두고 필요할 때만 켜기 | 기존 동작 유지 | 요구가 "꽉 채워라" 였고, 표가 카드보다 좁은 것은 대부분의 화면에서 버그처럼 보인다 | 기각 |

## 근거 (Rationale)

방식 선택은 **만들어 보고 눈으로 확인한 뒤** 바꿨다. "가장 넓은 컬럼이 흡수" 는 코드가 더 단순하고 px 를 보존한다는 장점이 있어 먼저 구현했지만, 실제 화면에서 급여 컬럼이 두 배 반으로 부푸는 것을 보고 기각했다. 컬럼 폭이 비슷한 업무 그리드에서는 "늘려도 어색하지 않은 컬럼" 이 존재하지 않는다는 것이 이유다.

비율 유지는 컨테이너 폭을 몰라도 계산된다는 점이 중요하다. 컬럼 빌더는 DOM 이 없는 시점에 동작하므로, 컨테이너 폭이 필요한 방식(고정 px + % 혼합)은 애초에 불가능했다.

`fill` 을 옵션으로 남긴 것은 기각한 방식이 **특정 상황에서는 정답**이기 때문이다. 비고·주소처럼 길어질 수 있는 텍스트 컬럼이 하나 있는 화면에서는 그 컬럼만 늘리는 것이 자연스럽다.

## 영향 (Consequences)

- 긍정: 표가 컨테이너를 정확히 채운다(1026px = 1026px 확인). 밴드(2단 헤더)·합계 행 정렬 오차 0px, 가로 스크롤 없음, 인라인 `max-width` 사라짐. 비율도 유지된다(197/144 = 150/110).
- 트레이드오프/비용:
  - **기본값이 `true` 이므로 기존 그리드의 컬럼 폭이 모두 비례 확대된다.** 지정한 px 를 그대로 쓰고 싶으면 `:fit-width="false"` 를 준다.
  - 컬럼 `width` 가 `'20.0000%'` 같은 문자열로 바뀌므로, `getState()` 로 저장된 폭을 px 로 가정하는 코드가 있으면 재확인이 필요하다.
  - DevExtreme 내부 조건문(`!hasAutoWidth`, `!hasPercentWidth`)에 의존한다. 메이저 업그레이드 시 재검증이 필요하다.
- 후속으로 따라오는 결정·제약:
  - **컬럼 폭 계산은 래퍼에서, 행번호 컬럼까지 포함한 최종 목록으로 한다.** 컬럼 빌더에서 100% 를 채워 두면 나중에 붙는 행번호 폭이 더해져 가로 스크롤이 생긴다.
  - **px 가 아닌 폭이 섞이면 손대지 않는다.** 사용자가 이미 %/auto 를 쓴 것은 의도가 있는 것이다.
  - 폭과 관련한 새 기능을 넣을 때 **인라인 스타일을 박는 지점을 먼저 확인한다.** 이 저장소에서 DevExtreme 이 인라인으로 쓰는 것은 지금까지 `textAlign`(헤더 정렬)과 `maxWidth`(표 폭) 두 곳이다.
