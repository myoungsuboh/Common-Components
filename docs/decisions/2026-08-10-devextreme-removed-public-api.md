# ADR-2026-08-10-devextreme-removed-public-api: 사라진 공개 메서드 대응

- 기록일: 2026-08-10 09:45
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: 없음
- 관련 plan: 없음

## 맥락 (Context)

래퍼가 `exportToExcel()` 을 노출하면서 아래처럼 위젯 메서드를 호출했다.

```js
exportToExcel: () => widget()?.exportToExcel?.(false),
```

데모에서 "엑셀 다운로드" 버튼을 눌렀으나 **파일도 안 생기고 오류도 없고 콘솔도 조용했다.** `exceljs` 청크 요청조차 발생하지 않았다.

소스를 확인한 결과 DevExtreme 26.1.3의 DataGrid에는 그 메서드가 없다.

- `dx.all.d.ts` 에 DataGrid 메서드로 존재하지 않는다(PivotGrid의 지역화 문구 키 `texts.exportToExcel` 만 남아 있다).
- 내부 `exportTo()` 는 `grids/data_grid/export/m_export.js` 에 있지만 `publicMethods()` 가 `['getDataProvider']` 만 반환하므로 외부에서 부를 수 없다.

옵셔널 체이닝(`?.`)을 썼기 때문에 없는 메서드를 불러도 예외 없이 `undefined`로 끝났다. 방어적으로 쓴 문법이 오히려 **실패를 숨겼다.**

같은 조사에서 `exportTo()` 가 `onExporting` 을 호출하고 끝이며 **`e.cancel` 을 읽지 않는다**는 것도 확인했다. 우리 핸들러가 마지막에 `e.cancel = true` 를 세우고 있었는데, 막아야 할 기본 동작이 애초에 없어 아무 의미가 없었다(게다가 `await` 뒤에 있어 동기 시점에는 반영되지도 않았다).

## 결정 (Decision)

1. 내보내기 로직을 `runExcelExport(component)` 함수로 분리하고, **툴바 버튼(`onExporting`)과 노출 API(`exportToExcel()`)가 같은 함수를 호출**한다. 위젯 메서드에 의존하지 않는다.
2. 의미 없는 `e.cancel = true` 를 제거하고, 왜 필요 없는지 주석으로 남긴다.
3. 라이브러리 메서드를 노출 API로 재수출할 때 **옵셔널 체이닝만 믿지 않고, 그 메서드가 실제 공개 API인지 타입 정의와 `publicMethods()` 에서 확인**한다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 내보내기 로직을 함수로 분리해 양쪽에서 호출 | 경로가 하나라 동작이 항상 일치한다. 위젯 공개 API 변화에 영향받지 않는다 | 툴바 버튼도 우리 코드를 거친다(원래도 `onExporting`으로 그랬다) | 채택 |
| 툴바의 내보내기 버튼을 코드로 클릭 | 라이브러리 흐름을 그대로 씀 | DOM 구조에 의존하고, `export.enabled`가 꺼져 있으면 버튼이 없어 동작하지 않는다 | 기각 |
| 내부 `exportTo()` 를 강제로 호출 | 한 줄 | 비공개 메서드. 업그레이드 시 조용히 깨진다 | 기각 |
| 프로그램 호출 API를 없애고 툴바만 제공 | 단순 | 그리드 밖 버튼으로 내보내는 화면이 많다. 요구사항에 맞지 않는다 | 기각 |

## 근거 (Rationale)

한 기능에 경로가 둘이면(툴바 / 노출 API) 둘 중 하나만 조용히 죽는 일이 생긴다. 실제로 이번에 툴바는 정상이고 노출 API만 죽어 있었는데, 데모의 완료 메시지가 안 뜨는 것 말고는 증상이 없어서 **버튼을 눌러보기 전까지 발견되지 않았다.** 경로를 하나로 합치면 이런 불일치가 구조적으로 불가능해진다.

`?.` 에 대한 교훈도 남길 만하다. 존재를 모르는 메서드에 옵셔널 체이닝을 걸면 "없으면 조용히 넘어간다"가 되는데, 이는 방어가 아니라 **관측 불가능한 실패**다. 라이브러리 API를 재수출하는 자리에서는 존재 여부를 먼저 확인해야 한다.

## 영향 (Consequences)

- 긍정: 툴바 버튼과 `exportToExcel()` 이 같은 결과를 낸다(검증: `사원목록.xlsx` 10,427바이트 생성, `on-export-complete` 이벤트가 부모까지 도달). `exceljs`는 여전히 지연 청크로 분리된다.
- 트레이드오프/비용: 없음. 코드가 오히려 줄었다.
- 후속으로 따라오는 결정·제약:
  - **라이브러리 메서드를 `defineExpose` 로 재수출할 때는 존재를 먼저 확인한다.** 타입 정의와 `publicMethods()` 를 본다.
  - **한 기능에 경로가 둘 이상이면 공통 함수로 합친다.** 각자 구현하지 않는다.
  - 노출 API는 데모에 버튼을 두어 **실제로 눌러 확인**한다. 조용한 실패는 코드 리뷰로 잡히지 않는다.
