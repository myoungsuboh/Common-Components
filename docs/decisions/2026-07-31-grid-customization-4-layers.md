# ADR-2026-07-31-grid-customization-4-layers: 커스터마이징 4계층 구조와 이식성 격리

- 기록일: 2026-07-31 11:48
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: 없음
- 관련 plan: 없음

## 맥락 (Context)

이 컴포넌트의 목적은 "여러 프로젝트에 투입할 때 사용자가 편하게 쓰는 것"이다. 공통 컴포넌트가 실패하는 전형적인 이유는 두 가지다. (1) 래퍼가 원본 기능을 가려서 예상 못 한 요구가 오면 아예 못 쓰게 되는 것, (2) 반대로 아무것도 감싸지 않아 래퍼의 존재 이유가 없는 것. 또한 이 저장소는 Vuetify·vue-i18n을 쓰지만 투입 대상 프로젝트가 같은 스택이라는 보장이 없다. SlickGrid 원본 컬럼 정의는 장황해서(금액 하나 표시하려면 formatter·params·cssClass·headerCssClass·type·editor.model·filter.model을 매번 작성) 그대로 노출하면 편해지지 않는다.

## 결정 (Decision)

커스터마이징을 아래로 갈수록 자유도가 커지는 4계층으로 설계하고, `src/components/SlickGrid/` 폴더가 Vuetify·vue-i18n에 의존하지 않게 격리한다(Vuetify는 데모 페이지에서만 사용).

```text
1층 축약   :columns="[{ field:'salary', header:'급여', type:'amount' }]"
2층 통과   :options="{ frozenColumn: 1 }"          (GridOption 전체 deep merge, 항상 기본값을 이김)
3층 슬롯   <template #header> / #footer
4층 탈출구 @on-grid-created / ref 명령형 API        (원본 Grid·DataView·Service 인스턴스 노출)
```

컴포넌트명은 라이브러리명을 그대로 쓴 `SlickGrid`으로 한다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 4계층 (축약 + 통과 + 슬롯 + 탈출구) | 흔한 케이스는 짧게, 예외는 항상 우회 가능 | 계층이 많아 문서화 부담 | 채택 |
| 축약 props만 노출 (화이트리스트) | API가 단순·명확 | 우리가 예상 못 한 옵션을 쓸 방법이 없어 결국 컴포넌트를 버리게 됨 | 기각 |
| 원본 GridOption만 그대로 통과 | 구현이 거의 없음 | 장황함이 그대로 남아 공통 컴포넌트 가치가 없음 | 기각 |
| 컴포넌트명 `Grid` (기능명 규칙) | 라이브러리를 교체해도 사용처 코드가 안 바뀜, 기존 관례(TinyMCE 래퍼를 `Webeditor`로 명명)와 일치 | 마이그레이션 대상이 "SlickGrid을 쓴다"고 지정된 상황에서 무엇을 쓰는지 즉시 드러나지 않음 | 기각 |

## 근거 (Rationale)

4층(탈출구)이 있으면 래퍼가 절대 병목이 되지 않는다. `slickgrid-vue`는 초기화 시 `Grid`/`DataView`/각종 Service를 이벤트로 노출하므로 이를 그대로 상위로 흘려주면 된다. 그 안전망이 있기 때문에 1층 축약을 과감하게 단순화할 수 있다 — 축약이 부족해도 막히지 않으니까. 2층 deep merge에서 **배열은 병합하지 않고 교체**한다. `externalResources` 같은 배열을 병합하면 서비스 인스턴스가 중복 등록되기 때문이다.

Vuetify 비의존은 여러 프로젝트 투입이라는 목적에서 곧바로 따라온다. 폴더째로 복사하면 동작해야 한다. 컴포넌트명은 `Grid`가 기존 관례와 더 맞지만, 사용자가 "SlickGrid 컴포넌트"라고 반복해 지칭했고 대상 프로젝트가 SlickGrid 사용을 명시적으로 요구하므로 명시성을 택했다.

## 영향 (Consequences)

- 긍정: 흔한 케이스는 `{ field, header, type }` 세 개로 끝나고, 예외 상황에서도 원본 API로 내려갈 수 있다. 폴더 복사만으로 다른 프로젝트에서 동작한다.
- 트레이드오프/비용: 같은 목적을 이루는 경로가 여러 개라서 어느 계층을 써야 하는지 문서로 안내해야 한다(데모 페이지가 그 역할). 라이브러리를 교체하면 컴포넌트명이 실제와 어긋난다.
- 후속으로 따라오는 결정·제약:
  - `SlickGrid/` 안에서 Vuetify 컴포넌트·vue-i18n을 import하지 않는다. 필요한 문구는 컴포넌트 내부 상수로 둔다.
  - 축약 변환기는 모르는 키를 삭제하지 않고 그대로 원본 Column으로 통과시킨다(1층과 2층이 충돌하지 않게).
  - `deepMerge`에서 배열은 항상 교체한다.
  - 순수 JS 프로젝트라 컬럼 정의에 타입 검사가 없으므로, 축약 정의에 런타임 유효성 경고를 함께 둔다.
