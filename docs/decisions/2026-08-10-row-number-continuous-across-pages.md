# ADR-2026-08-10-row-number-continuous-across-pages: 연속 행번호와 비공개 API 의존 판단

- 기록일: 2026-08-10 11:35
- 상태: 승인됨
- 단계(Origin): dev (execute-dev)
- 관련 spec: 없음
- 관련 plan: 없음

## 맥락 (Context)

행번호(No) 컬럼이 페이지를 넘길 때마다 1부터 다시 시작했다. SlickGrid·DevExtreme 두 컴포넌트가 같았다. 원인은 두 라이브러리 모두 셀 렌더러에 **"지금 그려진 행들 안에서의 순번"** 을 넘기기 때문이다.

조사하면서 문제가 페이징만이 아니라는 것이 드러났다. **DevExtreme 가상 스크롤에서도** 아래로 스크롤하면 번호가 1부터 다시 시작했다(60행 그리드에서 37번째 행이 맨 위일 때 No 가 1,2,3,4,5).

그래서 "앞쪽에 몇 개가 있었는지(offset)" 를 구해야 하는데, DevExtreme 가상 스크롤에서는 그 값을 주는 공개 API 가 없었다. 37번째 행이 맨 위인 상태에서 후보를 전부 실측했다(필요값 36).

| 후보 | 실측값 | 판정 |
|------|--------|------|
| `pageIndex() * pageSize()` | 20 | 어긋남 — 여러 페이지를 한 뷰포트에 걸쳐 읽는다 |
| `getVisibleRows()[0].rowIndex` | 0 | 창 기준 |
| `getRowIndexByKey(key)` | 4 | 창 기준 |
| `getDataSource().lastLoadOptions()` | `null` | 로컬 배열에서는 채워지지 않는다 |
| `rowRenderingMode: 'standard'` 로 변경 | 35 vs 20 | 여전히 창 단위로 그린다 |
| 데이터 컨트롤러 `getRowIndexOffset()` | **36** | 정확 — DevExtreme 자신이 쓰는 값 |

`getRowIndexOffset()` 은 `publicMethods()` 목록에 없다(= 비공개).

SlickGrid 쪽에도 함정이 있었다. `dataView.getPagingInfo()` 는 로컬 페이징에서만 맞는다. 서버 페이징에서는 `PaginationService` 가 `dataView.setPagingOptions()` 를 호출하지 않아 `pageNum`/`pageSize` 가 0 으로 남는다.

## 결정 (Decision)

1. **행번호는 페이지·스크롤에 걸쳐 연속되게 한다.** 정렬·필터를 걸면 화면에 보이는 순서대로 다시 매겨지는 동작은 유지한다.
2. **SlickGrid** — `createRowNumberColumn` 이 `getOffset` 을 받고, 래퍼가 `paginationService.dataFrom - 1` 을 넘긴다. `dataFrom` 은 `recalculateFromToIndexes()` 가 로컬·서버 두 경로 모두에서 갱신하므로 코드가 하나로 끝난다. `getPagingInfo()` 는 쓰지 않는다.
3. **DevExtreme** — `rowNumberOffset(grid)` 로 분기한다.
   - 페이징 모드: `pageIndex() * pageSize()` (둘 다 공개 메서드)
   - 가상/무한 스크롤: 데이터 컨트롤러의 `getRowIndexOffset()`
4. **비공개 API 는 아래 조건을 모두 만족할 때만 읽는다.**
   - 공개 API 로 같은 값을 구할 수 없음을 **실측으로 확인**했다
   - **읽기 전용**이다 (라이브러리 상태를 바꾸지 않는다)
   - 옵셔널 체이닝으로 감싸 **없어져도 예외가 나지 않는다**
   - 사라졌을 때의 **열화 동작이 안전하다** (여기서는 오프셋 0 → 예전처럼 스크롤 시 1부터, 화면이 깨지지 않는다)
   - 어떤 후보를 왜 버렸는지 **코드 주석에 실측값과 함께** 남긴다
5. **가상 스크롤에서 `paging.enabled: false` 를 주지 않는다.** DevExtreme 의 가상 스크롤은 내부적으로 페이징으로 데이터를 나눠 읽으므로, 끄면 오프셋의 기준이 사라진다. 페이저만 숨긴다.

## 고려한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 채택 여부 |
|------|------|------|-----------|
| 공개 API + 가상 스크롤만 비공개 getter | 두 모드 모두 정확하다. 비공개 의존이 한 줄로 격리된다 | 메이저 업그레이드 시 재검증 대상이 하나 늘어난다 | 채택 |
| 페이징만 고치고 가상 스크롤은 그대로 두기 | 공개 API 만 쓴다 | 가상 스크롤 그리드에서는 여전히 번호가 1부터 다시 시작한다. "번호가 이어진다" 는 설명과 화면이 어긋나 더 나쁘다 | 기각 |
| `rowRenderingMode: 'standard'` 로 바꿔 공개 API 로 계산 | 비공개 의존 없음 | 실측 결과 여전히 창 단위로 그려 오프셋이 맞지 않았다(35 vs 20). DOM 최적화만 잃고 문제는 그대로 | 기각 |
| 원본 데이터 배열에서 인덱스를 찾아 번호 매기기 (key→index 맵) | 라이브러리에 전혀 의존하지 않음 | 정렬·필터를 걸면 "원본 순서" 가 나와 화면 순서와 어긋난다. 대용량에서 맵 관리 비용도 생긴다 | 기각 |
| `beginPageIndex()` 등으로 오프셋을 직접 재구현 | 공개에 가까운 API 조합 | DevExtreme 내부 계산(`skipForCurrentPage` 보정 등)을 추측으로 복제하는 것이라 조용히 어긋날 수 있다. 같은 값을 두 번 구현하는 셈 | 기각 |
| SlickGrid 에서 `dataView.getPagingInfo()` 사용 | 래퍼 상태를 안 거친다 | 서버 페이징에서 0 이 나온다. 두 경로를 따로 처리해야 한다 | 기각 |

## 근거 (Rationale)

핵심 판단은 **"비공개 API 를 읽을 것인가"** 였다. 기존 ADR(`library-extension-point-workarounds`)은 "전역 상태를 변형하지 말라", "라이브러리가 붙인 클래스를 지우지 말라" 를 정했지만 읽기 전용 내부 접근은 다루지 않았다.

여기서 읽기를 택한 이유는 대안이 모두 **틀린 값을 자신 있게 보여주는 쪽**이었기 때문이다. `pageIndex()*pageSize()` 로 폴백하면 37번째 행에 21 이 찍힌다 — 사용자는 이것을 "맞는 번호" 로 믿는다. 반면 오프셋 0 은 "스크롤하면 1부터" 라는, 이미 사용자가 문제로 인지한 익숙한 열화다. 그래서 폴백을 `pageIndex()*pageSize()` 가 아니라 0 으로 두었다.

후보를 하나씩 실측해 표로 남긴 것도 의도적이다. 다음 사람이 "공개 API 로 되지 않나?" 라고 다시 물을 때, 같은 조사를 반복하지 않도록 하기 위함이다.

SlickGrid 에서 `dataFrom` 을 고른 것은 로컬·서버 페이징이 **한 코드로** 끝나기 때문이다. `getPagingInfo()` 를 썼다면 서버 페이징에서 조용히 0 이 되어, 서버 페이징을 쓰는 화면에서만 번호가 틀리는 발견하기 어려운 버그가 됐을 것이다.

## 영향 (Consequences)

- 긍정: 두 컴포넌트의 행번호가 같은 규칙으로 동작한다. 검증 결과 — DevExtreme 페이징 3페이지 41~, 건수 35 로 바꾼 뒤 2페이지 36~70, 가상 스크롤에서 E00037 행의 No 37 / SlickGrid 로컬 2페이지 21~, 마지막 페이지 121~137, 서버 페이징(총 1,234건) 2페이지 21~.
- 트레이드오프/비용:
  - **행번호 의미가 바뀐다.** 이전에는 페이지마다 1부터였다. 화면 캡처나 문서가 옛 동작을 전제하고 있으면 갱신이 필요하다.
  - DevExtreme 비공개 메서드 `getRowIndexOffset()` 에 의존한다. 메이저 업그레이드 시 재검증 항목이다.
  - 가상 스크롤에서 `paging` 을 켠 상태로 두므로, `paging.pageSize` 가 가상 스크롤의 데이터 청크 크기로 쓰인다.
- 후속으로 따라오는 결정·제약:
  - **비공개 API 는 위 4항의 5개 조건을 모두 만족할 때만 읽는다.** 쓰기는 하지 않는다.
  - **폴백은 "그럴듯한 오답" 보다 "알아보기 쉬운 열화" 를 고른다.**
  - 라이브러리 값이 "화면 기준" 인지 "전체 기준" 인지 **문서만 보고 판단하지 않는다.** 이번에도 타입 정의의 "The visible index of the row" 만으로는 창 기준인지 페이지 기준인지 구분되지 않았고, 실제로 렌더해서 값을 읽어야 알 수 있었다.
  - 행번호처럼 두 컴포넌트가 공유하는 동작은 **한쪽만 고치지 않는다.**
